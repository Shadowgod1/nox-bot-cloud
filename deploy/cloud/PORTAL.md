# Портал Nox Bot (bot.noxsw.kz) — инструкция для техника

Портал — это сайт, где компании подают заявку на WhatsApp-бота, сотрудники Nox одобряют её, а бот
создаётся на облачном сервере сам, по адресу `https://<адрес>.noxsw.kz`.

## Как устроено

| Часть | Где | Что делает |
|---|---|---|
| `web` (nginx + сайт) | контейнер, `127.0.0.1:8100` | единственный вход снаружи: туннель Cloudflare `bot.noxsw.kz → http://127.0.0.1:8100` |
| `api` (FastAPI) | контейнер, без docker-сокета и без root | заявки, вход, письма, очередь заданий, LLM-шлюз `/llm/...`, продления и счета (фоновая задача раз в 5 минут); внутренний API для провизионера на `127.0.0.1:8099` (через туннель и nginx недоступен) |
| `db` (Postgres 16) | контейнер, только внутренняя сеть | данные портала, том `nox-portal_pg_data` |
| `nox-provisioner` | systemd на хосте, root, раз в 30 с | забирает одобренные заявки, запускает `iler-client.sh`, вписывает ключ шлюза, создаёт адрес в туннеле и DNS, сообщает результат порталу |

Секреты:

- `/opt/nox-portal/.env` (root, 600) — настройки портала, SMTP, `NOX_SECRET_KEY`, пароль БД и
  **настоящие ключи провайдеров** `NOX_UPSTREAM_*_KEY` (они есть только здесь).
- `/etc/nox-portal/provisioner.env` (root, 600) — токен провизионера, адрес шлюза, токен Cloudflare.
- `/etc/nox-portal/provisioner-key.pem` (root, 600) — закрытый ключ. Им провизионер расшифровывает
  ключи шлюза и персональные ключи Anthropic клиентов. Портал хранит их только зашифрованными открытым
  ключом (`/opt/nox-portal/provisioner-pub.pem`) и стирает после успешного задания.

Ключи и токены набирайте прямо на сервере. Не отправляйте их в чаты, тикеты и документы.

## 1. Установка

Нужен облачный сервер с Docker и распакованным релизом iler-bot в `/opt/iler/bundle`
(папка с `compose.yml`, `deploy/` и `images.tar`). Порталу нужна папка `portal/` из того же репозитория.

```sh
cd /opt/iler/bundle            # или клон репозитория iler-bot
sudo bash deploy/cloud/portal-install.sh
```

Скрипт можно запускать повторно: секреты и данные сохраняются, образы пересобираются.
Он создаёт `/opt/nox-portal`, генерирует секреты, поднимает контейнеры (проект `nox-portal`) и ставит
`nox-provisioner.service` с таймером.

Проверка: `curl -fsS http://127.0.0.1:8100/health` выводит `{"status":"ok",...}`.

## 2. Почта (SMTP)

Откройте `sudo nano /opt/nox-portal/.env` и заполните:

```
NOX_EMAIL_MODE=smtp
NOX_SMTP_HOST=smtp.example.kz
NOX_SMTP_PORT=587            # 465 для SSL
NOX_SMTP_SECURITY=starttls   # starttls | ssl | none
NOX_SMTP_USER=bot@example.kz
NOX_SMTP_PASSWORD=...        # пароль ящика или пароль приложения
NOX_SMTP_FROM=Nox service <bot@noxsw.kz>
NOX_SMTP_REPLY_TO=info@noxsw.kz   # необязательно: ответы клиентов уходят в этот ящик
NOX_STAFF_NOTIFY=ops@example.kz,boss@example.kz   # кому писать о новых заявках
```

Затем перезапустите: `sudo bash deploy/cloud/portal-install.sh`.
Чтобы письма не попадали в спам, у домена отправителя должны быть настроены SPF и DKIM.

`NOX_EMAIL_MODE=log` нужен только для проверки на тестовом стенде: письма с кодами и ссылками
пишутся в лог (`cd /opt/nox-portal && sudo docker compose logs api`). На боевом сервере этот режим не включайте.

## 2a. Тарифы, счета и оплата

После кода из письма клиент выбирает тариф и способ оплаты. Статусы заявки:

| Выбор клиента | Статус | Что дальше |
|---|---|---|
| Free (тест) | «Одобрена» сразу | бот создаётся без оплаты и без менеджера |
| платный тариф, «Оплата по счёту через менеджера» | «Ждёт счёта» | сотрудник выставляет счёт → «Ждёт оплаты» → «Отметить оплату» |
| платный тариф, «Оплатить онлайн» (только если подключён провайдер, раздел 2b) | «Оплата онлайн» | провайдер подтверждает оплату → бот создаётся сам |

Дальше как раньше: «Одобрена» → «Создаётся» → «Работает». Фильтры «Ждёт счёта», «Оплата онлайн», «Ждёт оплаты»
есть в списке заявок.

**Счета выставляет менеджер.** Портал сам счетов не создаёт. Когда клиент выбрал оплату по счёту, на
`NOX_STAFF_NOTIFY` приходит письмо «Клиент выбрал оплату по счёту». В карточке заявки есть блок «Выставить
счёт»: тариф, сумма (по умолчанию — цена тарифа, её можно изменить) и комментарий, который печатается в счёте.
Клиенту уходит письмо со счётом, статус меняется на «Ждёт оплаты». Счёт можно выставить заново: номер
сохранится, сумма обновится. Если клиент сменит тариф или способ оплаты, выставленный счёт отзывается, а его
номер достанется следующему счёту. Когда деньги пришли, нажмите «Отметить оплату» и введите сумму и номер
платёжки. Платёж записывается в журнал, бот сразу встаёт в очередь на создание.

- Тарифы (название, цена в ₸ в месяц, коины) лежат в одном месте:
  `portal/backend/nox_portal/tariffs.py`. После правки запустите `portal-install.sh` ещё раз. Уже выставленные
  счета сохраняют свою сумму.
- Реквизиты продавца для счёта — `NOX_SELLER_*` в `/opt/nox-portal/.env` (название, БИН, банк, ИИК,
  БИК, Кбе, адрес, телефон). В репозитории только заглушки. Срок оплаты — `NOX_INVOICE_DUE_DAYS`.
- Журнал платежей (таблица `payments`) только дополняется: изменить или удалить строку база не даст.
  Ошибку или возврат оформляют новой строкой с отрицательной суммой (пока через SQL, кнопки в интерфейсе нет).
  Способ оплаты в строке: `invoice` (отметил сотрудник) или `online:<провайдер>`.
- «Одобрить без оплаты» остаётся для партнёров и оплаты вне портала. Коины по умолчанию берутся из тарифа
  клиента, в журнал действий попадает `payment: null`.
- Заявки, которые до обновления получили счёт автоматически («Ждёт оплаты»), работают как раньше:
  «Отметить оплату» и страница счёта не изменились.

### Free (тест)

Тариф `free`: 0 ₸, 2 000 коинов на весь тест, без продления. Клиент выбирает его сам, бот создаётся сразу
(в журнале — `client.auto_free`), сотрудникам приходит уведомление «Подключён тест (Free)». Защита от
злоупотреблений:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `NOX_FREE_TARIFF_PUBLIC` | `true` | `false` — клиенты Free не видят; сотрудник может назначить его сам: «Одобрить» с тарифом Free или «Локальная установка» |
| `NOX_FREE_MAX_ACTIVE` | `5` | сколько тестов одновременно в статусах «Одобрена», «Создаётся», «Работает». Если места кончились, клиент видит «Тестовые места закончились, выберите тариф или напишите менеджеру» |
| `NOX_FREE_DAYS` | `14` | через сколько дней тест приостанавливается |

Один тест на e-mail и на номер телефона (сравниваются только цифры, `8…` считается как `7…`) навсегда.
Повторная попытка получает понятный отказ. Когда тест кончился, фоновая задача приостанавливает бота
(причина «закончился тест», облачному боту ставится задание приостановки). Клиенту уходит письмо «Тестовый
период закончился» со ссылкой на кабинет, сотрудникам — уведомление.

Переход на платный тариф идёт из кабинета, бот остаётся тот же. Клиент выбирает тариф и способ оплаты.
- **По счёту.** Сотрудникам приходит письмо «Переход с Free на платный тариф». В карточке есть блок «Переход
  на платный тариф» → «Выставить счёт» (счёт вида «Переход на тариф»).
- **Онлайн.** Счёт на переход создаётся сразу и оплачивается у провайдера.

После оплаты начинается платный период с коинами тарифа, приостановка снимается (задание возобновления).

### Пополнение и продление

- «Пополнить» в кабинете: «Оплатить онлайн» (если подключён провайдер) или «Счёт через менеджера». Второй
  вариант создаёт запрос: сотрудникам приходит письмо, в карточке появляется «Клиент запросил пополнение» и
  кнопка «Выставить счёт на пополнение» (по умолчанию пакет 10 000 коинов за 9 900 ₸, сумму и коины можно
  изменить). Пока счёт не оплачен, повторное «Пополнить» открывает его.
- Продление: за `NOX_RENEWAL_INVOICE_DAYS` (5) дней до конца периода клиенту приходит напоминание, а сотрудникам —
  «Пора выставить счёт на продление» со ссылкой на карточку. В карточке появляется блок с кнопкой «Выставить
  счёт». Отсрочка и приостановка за неоплату работают как раньше (раздел 8). Free не продлевается.
- Любой выставленный счёт клиент может оплатить онлайн кнопкой «Оплатить онлайн», если провайдер подключён.
  Банковский перевод по этому счёту тоже остаётся в силе.

## 2b. Онлайн-оплата

Онлайн-оплата выключена, пока не задан провайдер. Тогда кнопки «Оплатить онлайн» нет, клиенты платят по
счёту. Настройка в `/opt/nox-portal/.env`:

| Переменная | Значение |
|---|---|
| `NOX_PAYMENT_PROVIDER` | пусто или `none` — выключено; `kaspi` — Kaspi QR (ниже); `mock` — тестовая касса (только для стенда) |
| `NOX_PAYMENT_MOCK_ALLOWED` | `true` разрешает `mock` при `NOX_EMAIL_MODE=smtp`. Без него `mock` работает только при `NOX_EMAIL_MODE=log`. На боевом сервере не включайте |
| `NOX_PAYMENT_MOCK_RECURRING` | `true` — mock притворяется, что провайдер выдаёт токен для повторных списаний (только для тестов) |

Неизвестный или запрещённый провайдер не мешает порталу запуститься: в логе будет ошибка, онлайн-оплата
останется выключенной.

Как это работает:

1. Клиент жмёт «Оплатить онлайн». Портал создаёт строку в `online_payments` и получает у провайдера страницу
   оплаты или QR. Номер карты и CVV портал не видит и не хранит никогда.
2. Провайдер присылает результат на `https://bot.noxsw.kz/api/payments/webhook/<провайдер>`. Адрес открыт
   наружу через nginx, но с лимитом запросов. Портал проверяет подпись: без верной подписи — `401`, ничего не
   меняется.
3. «Оплачено»: в журнал платежей пишется строка `online:<провайдер>`, и выполняется то же, что делает «Отметить
   оплату». Новая заявка одобряется, бот встаёт в очередь. Пополнение начисляет коины, продление продлевает
   период, переход с Free включает платный тариф. Повтор того же уведомления ничего не делает: учёт идёт по
   номеру платежа у провайдера.
4. «Отказ» отмечает платёж как неудачный, статус заявки не меняется. Клиент может оплатить снова или выбрать счёт.
5. Каждое принятое уведомление записывается в `payment_events`: хэш тела и несколько полей, без самого тела.
   Таблица только дополняется. Если сумма не совпала, оплата пришла по уже одобренной заявке или был возврат,
   сотрудникам приходит письмо «Онлайн-оплата требует внимания». Возврат добавляет строку с минусом, бот не
   останавливается.

Тестовая касса (`mock`): «Оплатить онлайн» открывает страницу `/pay/mock/…` с кнопками «Оплачено» и «Отказ».
Страница отправляет подписанное уведомление через тот же публичный адрес, что и настоящий провайдер. Проверка
на стенде: `NOX_EMAIL_MODE=log`, `NOX_PAYMENT_PROVIDER=mock`, затем регистрация → тариф → «Оплатить онлайн» →
«Оплачено» → в карточке заявки видна онлайн-оплата, бот в очереди.

Настоящий провайдер подключается отдельным модулем в `portal/backend/nox_portal/payments/` (интерфейс в
`payments/base.py`, регистрация в `payments/__init__.py`).

### Kaspi (каркас, протокол не сверен)

На старте онлайн-оплата — только Kaspi, по схеме «Платежи на Kaspi.kz» для поставщика услуг. Портал
показывает QR, а на телефоне — ссылку «Открыть в Kaspi». Приложение Kaspi открывается на нашем сервисе с уже
заполненными кодом платежа и суммой. Kaspi спрашивает у портала `check` (есть ли такой счёт и сколько платить)
и сообщает `pay` (оплачено, номер `txn_id`).

- Код платежа — цифры номера счёта: `NOX-2026-00012` → `202600012`. Счёт при этом остаётся в силе и для
  банковского перевода.
- «Оплатить онлайн» при выборе тарифа сразу выставляет счёт на цену тарифа (статус «Оплата онлайн») и
  показывает QR. Так же работают пополнение и оплата любого выставленного счёта.
- `pay` выполняет то же, что «Отметить оплату». Сумма должна совпасть со счётом точно, частичных оплат нет.
  Повтор с тем же `txn_id` ничего не делает и возвращает тот же ответ. Оплаченный или неизвестный счёт —
  `result=5`.

| Переменная | Значение |
|---|---|
| `NOX_PAYMENT_PROVIDER=kaspi` | включает Kaspi |
| `NOX_KASPI_PAY_URL_TEMPLATE` | ссылка для QR с подстановками `{account}` и `{amount}`; точный адрес даст Kaspi по договору. Пусто — Kaspi выключен |
| `NOX_KASPI_ALLOWED_IPS` | адреса и подсети Kaspi через запятую. IP берётся из `CF-Connecting-IP` через nginx портала |
| `NOX_KASPI_BASIC_AUTH` | `логин:пароль` для HTTP Basic, если Kaspi это поддерживает |

Без `NOX_KASPI_ALLOWED_IPS` и без `NOX_KASPI_BASIC_AUTH` адрес `https://bot.noxsw.kz/api/payments/kaspi`
отклоняет все вызовы (`403`). Адрес открыт наружу через nginx с лимитом запросов.

**Не проверено.** Формат запросов и ответов (`command`, `txn_id`, `account`, `sum`, `txn_date` → `txn_id`,
`result`, `comment`, `prv_txn`; коды 0, 1, 4, 5, 241, 242, 300; ответ JSON) взят из типовой схемы
интеграторов. Официальный документ Kaspi ещё не получен. Когда он придёт, сверьте формат и правьте только
`payments/kaspi_protocol.py`. До этого с настоящим Kaspi не включайте.

## 2c. Поддержка, документы, помощь с настройкой

Настройки в `/opt/nox-portal/.env` (после правки — `sudo bash deploy/cloud/portal-install.sh`):

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `NOX_SUPPORT_PHONE` | пусто | телефон поддержки, как его показывать: `+7 700 000 00 00`. Виден в шапке и подвале портала, рядом с формой входа, в кабинете (блок «Нужна помощь?») и в подписи всех писем |
| `NOX_SUPPORT_WHATSAPP` | пусто | номер WhatsApp цифрами (`77000000000`), портал ведёт на `https://wa.me/<номер>`. Пусто — кнопки WhatsApp нет |
| `NOX_COINS_PER_DIALOG` | `20` | сколько коинов в среднем стоит один диалог. По нему тарифы и баланс в кабинете показывают «≈ N диалогов» (округлённо: 2 000 коинов ≈ 50, 30 000 ≈ 800) |
| `NOX_LEGAL_DATE` | пусто | дата редакции оферты, политики возврата и конфиденциальности, например `01.12.2026`. Пусто — на страницах плашка «Черновик» |

**Документы.** Страницы `/offer`, `/refund`, `/privacy` собираются из `portal/web/src/legal/*.md` (копия
черновиков из `iler-vault/legal`). Правите текст — правьте эти файлы и пересоберите портал. Реквизиты в
квадратных скобках (наименование, БИН, адрес, банк, ИИК, БИК, Кбе, телефон) подставляются из `NOX_SELLER_*`.
Заглушки из `.env.example` (нули, `XXXX`, «Примерная») и одно «Nox service» вместо юрлица не подставляются,
скобки остаются. Остальные скобки (сроки, часы работы) правятся в самих файлах. Ссылки на документы — в подвале
и в галочке согласия при регистрации.

**«Настроим за вас».** В кабинете подключённого бота есть кнопка «Попросить помочь с настройкой». Нажатие пишет
в журнал `client.setup_help_requested` и шлёт одно письмо на `NOX_STAFF_NOTIFY` («Просят помочь с настройкой»).
Повторные нажатия, пока запрос открыт, писем не шлют. В карточке заявки появляется блок «Помощь с настройкой»
с датой и кнопкой «Отметить, что связались» (`staff.setup_help_contacted`). После этого клиент может попросить
снова. Цена в кабинете не называется: её озвучивает менеджер.

**Напоминания о конце теста.** За 3 дня и за сутки до конца Free клиенту приходит письмо «Nox Bot: тест
закончится …»: бот перестанет отвечать, настройки и переписка сохранятся, после оплаты бот продолжит с того же
места. Каждое письмо уходит один раз (колонка `accounts.trial_notice_days`, журнал `billing.trial_reminder`).
Если тест короче трёх дней, придёт только ближайшее.

**Адрес бота при регистрации** подставляется из названия компании латиницей (без «ТОО», «ИП», кавычек), клиент
может его поправить. Если адрес занят или зарезервирован, форма предлагает свободный вариант (`salon-2`).

Миграция `0005_onboarding.sql` только добавляет колонки (`setup_help_*`, `trial_notice_days`) и применяется
сама при старте api.

**Один вход для кабинета и панели.** Клиент регистрируется один раз, в портале. Создавая бота, портал
передаёт провизионеру владельца из заявки: e-mail, контактное лицо, компанию и хэш пароля кабинета (argon2id,
портал и ядро бота хэшируют одной библиотекой). Всё это отдаёт только внутренний API на `127.0.0.1:8099`.
Провизионер передаёт данные в `iler-client.sh create` через переменные окружения (`ILER_OWNER_EMAIL`,
`ILER_OWNER_NAME`, `ILER_COMPANY`, `ILER_OWNER_PASSWORD_HASH`), а не через командную строку. Скрипт вписывает
их в `.env` бота (права 600). Ядро при первом старте создаёт владельца, если пользователей ещё нет. Потом
провизионер стирает хэш из `.env` и перезапускает ядро.

- В кабинете у работающего бота — кнопка «Открыть панель бота» (вход в панель с подставленным e-mail) и
  надпись «Вход — тем же e-mail и паролем, что в кабинете». Одноразовой ссылки нет. В письме «Ваш бот готов»
  написано то же.
- Мастер настройки в панели начинается с шага «Языковая модель». Компания из заявки уже стоит в поле
  «Название» шаблона.
- **Смена пароля в кабинете на панель не влияет.** Пароль от панели меняется в самой панели. Об этом есть
  подсказка в кабинете.
- Если владелец в боте уже есть, данные из `.env` ядро не трогает.
- **Старые боты** (созданы до этого обновления, `owner_preset = false`) работают как раньше: одноразовая
  ссылка в кабинете и в письме. Если ядро не создало владельца (старый релиз бота, хэш не argon2id), провизионер
  сообщает обычную одноразовую ссылку.

Миграция `0006_owner_preset.sql` добавляет колонку `accounts.owner_preset` (по умолчанию `false`) и применяется
сама при старте api.

## 3. Cloudflare

### Токен API

Cloudflare → My Profile → API Tokens → Create Token → Custom token:

| Тип | Ресурс | Право |
|---|---|---|
| Account | Cloudflare Tunnel | Edit |
| Zone | DNS | Edit |

В Zone Resources выберите только зону `noxsw.kz`, в Account Resources — только аккаунт Nox.

Также нужны:

- **Account ID** — на странице зоны noxsw.kz справа (Overview → API);
- **Zone ID** — там же;
- **Tunnel ID** — Zero Trust → Networks → Tunnels → `iler-cloud-01` (UUID).

Впишите их в `sudo nano /etc/nox-portal/provisioner.env`: `CF_API_TOKEN`, `CF_ACCOUNT_ID`,
`CF_ZONE_ID`, `CF_TUNNEL_ID`. `NOX_GATEWAY_URL` (по умолчанию `https://bot.noxsw.kz`) — адрес
LLM-шлюза, который получат новые боты (раздел 8). `NOX_DEFAULT_ANTHROPIC_KEY` оставьте пустым: он нужен
только для заданий, поставленных до появления шлюза.

Провизионер для каждого бота:

1. читает конфигурацию туннеля (`GET /accounts/{account}/cfd_tunnel/{tunnel}/configurations`);
2. добавляет правило `<адрес>.noxsw.kz → http://127.0.0.1:<порт>` перед последним правилом
   `http_status:404` и отправляет весь список обратно (`PUT` на тот же адрес). Остальные правила
   сохраняются;
3. создаёт DNS-запись `CNAME <адрес> → <tunnel-id>.cfargotunnel.com` с проксированием (оранжевое облако).

Если на этот адрес уже есть чужая DNS-запись, провизионер её не трогает и выдаёт ошибку.

Проверка настроек (ничего не меняет):

```sh
sudo bash -c 'set -a; . /etc/nox-portal/provisioner.env; python3 /opt/nox-portal/bin/nox-provisioner.py check'
```

После успешной проверки включите таймер: `sudo systemctl enable --now nox-provisioner.timer`.

### Адрес самого портала

Добавьте его один раз вручную: Zero Trust → Networks → Tunnels → `iler-cloud-01` → Public Hostname → Add.
Subdomain `bot`, Domain `noxsw.kz`, Service **HTTP** `127.0.0.1:8100`.

Внутренний порт `8099` в туннель не добавляйте никогда.

## 5. Проверка всей цепочки

1. Откройте `https://bot.noxsw.kz/register` и подайте заявку на свою почту с адресом вроде `test-nox`.
2. Введите код из письма, выберите тариф и «Оплата по счёту через менеджера». На `NOX_STAFF_NOTIFY` придёт
   письмо «Клиент выбрал оплату по счёту».
3. Войдите как сотрудник, откройте заявку (фильтр «Ждёт счёта»), нажмите «Выставить счёт». Клиенту придёт
   письмо со счётом, в кабинете откроется «Открыть счёт (PDF)». Затем нажмите «Отметить оплату» и укажите
   сумму и номер платёжки.
4. В течение минуты статус станет «Создаётся», а через несколько минут — «Работает».
   Ход работы: `sudo journalctl -u nox-provisioner -f`.
5. Придёт письмо «Ваш бот готов» с адресом панели. В кабинете нажмите «Открыть панель бота»: откроется
   вход в панель `https://test-nox.noxsw.kz` по HTTPS с уже подставленным e-mail. Войдите паролем от кабинета —
   откроется мастер настройки без шага «Владелец», в поле «Название» уже стоит компания из заявки.
6. Удалите тестового бота: в карточке заявки нажмите «Удалить бота» и введите адрес. Проверьте, что
   правило и CNAME исчезли в Cloudflare.

Если создание не удалось, статус станет «Ошибка». Текст ошибки виден в карточке заявки и в
`journalctl -u nox-provisioner`. Исправьте причину и нажмите «Повторить создание». Если бот уже был
установлен, повтор его не пересоздаёт, а только доделывает оставшиеся шаги.

## 6. Резервная копия базы портала

```sh
sudo mkdir -p /opt/nox-portal/backups
cd /opt/nox-portal && sudo docker compose exec -T db pg_dump -U portal -d portal -Fc \
  > /opt/nox-portal/backups/portal-$(date +%Y%m%d-%H%M).dump
```

Ежедневно в 03:00 по Алматы (`/etc/cron.d/nox-portal-backup`):

```
CRON_TZ=Asia/Almaty
0 3 * * * root cd /opt/nox-portal && docker compose exec -T db pg_dump -U portal -d portal -Fc > /opt/nox-portal/backups/portal-$(date +\%Y\%m\%d).dump && find /opt/nox-portal/backups -name 'portal-*.dump' -mtime +14 -delete
```

Вместе с копией базы сохраняйте `/opt/nox-portal/.env` и всю папку `/etc/nox-portal/`. Без
`NOX_SECRET_KEY` не расшифровать неотправленные ссылки владельцев, а без `provisioner-key.pem` —
ключи клиентов, которые стоят в очереди.

Восстановление:

```sh
cd /opt/nox-portal && sudo docker compose exec -T db pg_restore -U portal -d portal --clean --if-exists < portal-YYYYMMDD.dump
```

## 8. LLM-шлюз и коины

Боты не держат настоящих ключей Anthropic, OpenAI и Gemini. Каждый бот получает свой **виртуальный
ключ** `nox_vk_…` и ходит в модели через портал:

| Бот обращается | Портал отправляет |
|---|---|
| `https://bot.noxsw.kz/llm/anthropic/...` | `https://api.anthropic.com/...` |
| `https://bot.noxsw.kz/llm/openai/...` | `https://api.openai.com/...` |
| `https://bot.noxsw.kz/llm/gemini/...` | `https://generativelanguage.googleapis.com/...` |

Шлюз проверяет виртуальный ключ (в `x-api-key`, `Authorization: Bearer` или `x-goog-api-key`; ключ в
адресе `?key=` отклоняется), подставляет ключ компании, пропускает запрос и ответ без изменений (потоковые
ответы — сразу, по событиям) и списывает коины по токенам из ответа. Бот видит баланс через
`GET /llm/v1/balance`. При нулевом балансе шлюз отвечает `402 insufficient_coins` ещё до запроса к
провайдеру, отозванный ключ или приостановленный клиент получают `401 key_revoked`.

Пропускаются только генерация, подсчёт токенов, эмбеддинги и список моделей. Файлы, batch, fine-tuning,
картинки и звук закрыты: их шлюз не умеет считать.

### Настройка (один раз)

В `sudo nano /opt/nox-portal/.env` впишите ключи компании (только здесь, больше нигде):

```
NOX_UPSTREAM_ANTHROPIC_KEY=sk-ant-api03-…
NOX_UPSTREAM_OPENAI_KEY=sk-proj-…
NOX_UPSTREAM_GEMINI_KEY=AIza…
NOX_ALERT_TELEGRAM_BOT_TOKEN=     # необязательно: тревоги и сводка ещё и в Telegram
NOX_ALERT_TELEGRAM_CHAT_ID=
```

Затем `sudo bash deploy/cloud/portal-install.sh`. Провайдер без ключа отвечает ботам `503`.
Ключи Anthropic лучше держать в отдельном workspace `nox-cloud` с автопополнением в консоли.

### Цены и коины

1 коин = $0.001 расхода модели. Таблица цен одна: `portal/backend/nox_portal/prices.py`. В ней те же
цены Claude, что и в ядре бота: claude-sonnet-5-5 — $2/$10 за 1 млн токенов, claude-haiku-5-5 —
$0.1/$0.5. Запись в кэш Anthropic считается как 1,25 цены входа, чтение — 0,1. Цены других моделей задаются в
`NOX_MODEL_PRICES` в том же формате, что `ILER_MODEL_PRICES` у бота:

```
NOX_MODEL_PRICES={"gpt-5.4-mini": [0.25, 2.0], "gemini-3.8-flash": [0.3, 2.5]}
```

Модель без цены никогда не идёт бесплатно: её считают по самой дорогой известной цене того же провайдера.
Если у провайдера нет ни одной цены — по $2/$10, как в ядре. В логе появляется предупреждение, строка
журнала помечается `priced = false`, а в ежедневной сводке перечислены такие модели. **OpenAI и Gemini
встроенных цен не имеют**: впишите их в `NOX_MODEL_PRICES` до запуска клиентов на этих провайдерах.

Каждое списание — строка в `llm_usage`, каждое начисление — в `coin_grants`. Обе таблицы только
дополняются, как `payments`. Баланс клиента складывается так: месячный пакет текущего периода +
остаток докупленных коинов + пополнения − расход.

### Периоды, продление, отсрочка

- Период — месяц с момента активации: оплата первого счёта, одобрение без оплаты или создание локальной
  установки. В начале периода начисляется месячный пакет (лимит коинов заявки, по умолчанию — из тарифа).
- За 5 дней до конца периода (`NOX_RENEWAL_INVOICE_DAYS`) клиенту приходит напоминание, а сотрудникам —
  «Пора выставить счёт на продление». Счёт выставляет сотрудник одной кнопкой в карточке (раздел 2a). Оплату
  он отмечает там же, в разделе «Продление и пополнение». Клиент может оплатить счёт и онлайн.
- В конце оплаченного периода начинается новый. Неиспользованный месячный пакет сгорает, докупленные коины
  остаются.
- Если счёт не оплачен, бот ещё 3 дня (`NOX_GRACE_DAYS`) работает на остатке. Потом аккаунт получает статус
  «Приостановлена» (причина «неоплата»): ключ отвечает `401`, облачному боту ставится задание
  приостановки, клиенту и сотрудникам уходят письма. Как только оплату отметят, начинается новый период
  (с этого дня) и ставится задание возобновления.
- Когда остаётся 20% и 5% пакета, клиенту приходит письмо.
- Всё это делает фоновая задача портала (`NOX_BILLING_TICK_SECONDS`, по умолчанию 300 с). Провизионер
  в этом не участвует, он только выполняет задания приостановки и возобновления.

### Пополнение

В кабинете (`https://bot.noxsw.kz/cabinet`, сюда же ведёт кнопка «Пополнить» в админке бота) клиент жмёт
«Пополнить». Дальше он платит онлайн или просит счёт у менеджера (раздел 2a). Пакет — 10 000 коинов за 9 900 ₸
(`tariffs.TOPUP`). Коины начисляются сразу после оплаты, клиенту уходит письмо.

### Ключи ботов

- **Облако.** При «Отметить оплату» или «Одобрить» портал выпускает ключ и передаёт его провизионеру в
  зашифрованном виде. Провизионер вписывает в `.env` бота (права 600) `ILER_LLM_GATEWAY_URL` (из
  `NOX_GATEWAY_URL`), `ILER_LLM_GATEWAY_KEY` и `ILER_TOPUP_URL` (кнопка «Пополнить» в админке бота, из
  `NOX_TOPUP_URL`), очищает `ILER_ANTHROPIC_KEY` / `ILER_OPENAI_KEY` /
  `ILER_GEMINI_KEY`, ставит `ILER_MONTHLY_COINS=0` (коины считает портал) и перезапускает `iler-core`.
- **Свой ключ Anthropic клиента** (поле при одобрении) по-прежнему работает и имеет приоритет. Тогда шлюз
  не используется: виртуальный ключ не выпускается, переменные шлюза не пишутся, коины портал не считает.
- **«Перевыпустить ключ»** (карточка, раздел «LLM-шлюз»). Облачный бот получает задание «Новый ключ
  шлюза»: новый ключ вписывается в `.env` и ядро перезапускается. Старый ключ отключается только после
  успеха, если задание упало — отключается новый. Так же можно перевести на шлюз старого бота с ключом
  Anthropic в `.env`: после задания ключ компании на нём не останется. Для облачного бота кнопка
  доступна, только когда бот работает.
- **«Отозвать»** отключает все ключи сразу: бот получает `401` на каждый запрос к модели.
- В карточке видно только начало ключа (`nox_vk_AbCdEf…`). Целиком ключ портал не хранит: в базе лежит
  только его хэш SHA-256.

### Локальная установка (бот у клиента)

1. Сотрудник: «Заявки» → «Локальная установка». Заполните компанию, контакт, e-mail, короткое имя и
   тариф. Портал создаёт активный аккаунт без заданий провизионера и **один раз** показывает ключ.
   Клиенту уходит письмо о том, как задать пароль кабинета (через «Забыли пароль»).
2. Передайте ключ технику, не через мессенджеры. Если ключ потерян, нажмите «Перевыпустить ключ»: у
   локальной установки старый отключится сразу.
3. Техник на компьютере клиента вписывает в `/opt/iler/.env` две переменные ядра бота и перезапускает его:

   ```
   ILER_LLM_GATEWAY_URL=https://bot.noxsw.kz
   ILER_LLM_GATEWAY_KEY=nox_vk_…
   ILER_TOPUP_URL=https://bot.noxsw.kz/cabinet
   ```

   ```sh
   cd /opt/iler && sudo docker compose up -d --no-build iler-core
   ```

   Настоящие ключи `ILER_*_KEY` на машине клиента не нужны. Если они там остались, очистите их.
4. Проверка с машины клиента: `curl -s -H "x-api-key: nox_vk_…" https://bot.noxsw.kz/llm/v1/balance`
   должен вернуть `"status":"active"` и остаток коинов.

### Тревоги и сводка

Сотрудникам из `NOX_STAFF_NOTIFY` и в Telegram (если задан) уходят тревоги:

- провайдер отклонил ключ компании (`401`/`403`): проверьте `NOX_UPSTREAM_*_KEY`;
- закончились деньги или квота у провайдера (`402`, «credit balance», «insufficient_quota»): пополните
  консоль;
- 5 и больше ошибок 5xx или таймаутов за 5 минут (`NOX_ALERT_ERROR_THRESHOLD`, `NOX_ALERT_WINDOW_SECONDS`).

Одна и та же тревога повторяется не чаще раза в 30 минут. Каждый день после 09:00 по Алматы приходит
сводка за вчера: коины и доллары по провайдерам, токены, модели без цены. Сверяйте её с консолями
провайдеров. Токен Telegram в логи не попадает.

### Ограничения

- 60 запросов в минуту на ключ (`NOX_GATEWAY_RATE_PER_MINUTE`), запрос до 10 МБ (`NOX_GATEWAY_MAX_BODY_BYTES`;
  в `portal/web/nginx.conf` стоит тот же `client_max_body_size 10m`). При превышении шлюз отвечает `429` или `413`.
- Параллельные запросы одного клиента могут уйти в минус не больше чем на один запрос. Перед запросом
  резервируется верхняя оценка его цены, а при нулевом остатке после всех резервов шлюз отвечает `402`.
  Небольшой минус прощается при смене периода.
- Если клиент не попросил usage в потоке OpenAI Chat Completions, шлюз добавляет
  `stream_options.include_usage` и не пересылает клиенту лишний последний чанк с пустым `choices`.
- У OpenAI кэшированные входные токены считаются по полной цене входа. Токены «размышлений» Gemini
  (`thoughtsTokenCount`) считаются как выход.

### Проверка на своём компьютере (mock, без настоящих ключей)

`portal/smoke/` содержит фальшивый API провайдеров и сценарий проверки. Скопируйте `portal/.env.example` в
`portal/.env`, задайте `NOX_SECRET_KEY` (`openssl rand -base64 32`), `NOX_DB_PASSWORD`,
`NOX_EMAIL_MODE=log`, `NOX_PUBLIC_URL=http://127.0.0.1:18100`, `NOX_HTTP_PORT=18100`,
`NOX_INTERNAL_PORT=18099`. Положите любой открытый RSA-ключ в `portal/provisioner-pub.pem` и выполните:

```sh
cd portal
docker compose -p nox-smoke -f compose.yml -f smoke/compose.smoke.yml --env-file .env up -d --build
bash smoke/run.sh
docker compose -p nox-smoke -f compose.yml -f smoke/compose.smoke.yml --env-file .env down -v
```
