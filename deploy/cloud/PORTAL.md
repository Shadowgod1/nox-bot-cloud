# Портал Nox Bot (bot.noxsw.kz) — инструкция для техника

Портал — это сайт, где компании подают заявку на WhatsApp-бота, сотрудники Nox одобряют её, а бот
создаётся на облачном сервере сам, по адресу `https://<адрес>.noxsw.kz`.

## Как устроено

| Часть | Где | Что делает |
|---|---|---|
| `web` (nginx + сайт) | контейнер, `127.0.0.1:8100` | единственный вход снаружи: туннель Cloudflare `bot.noxsw.kz → http://127.0.0.1:8100` |
| `api` (FastAPI) | контейнер, без docker-сокета и без root | заявки, вход, письма, очередь заданий, LLM-шлюз `/llm/...`, продления и счета (фоновая задача раз в 5 минут); внутренний API для провизионера на `127.0.0.1:8099` (через туннель и nginx недоступен) |
| `db` (Postgres 16) | контейнер, только внутренняя сеть | данные портала, том `nox-portal_pg_data` |
| `nox-provisioner` | systemd на хосте, root, раз в 30 с | забирает одобренные заявки, запускает `iler-client.sh`, вписывает ключ шлюза, создаёт адрес в туннеле и DNS, сообщает результат порталу |

Секреты:

- `/opt/nox-portal/.env` (root, 600) — настройки портала, SMTP, `NOX_SECRET_KEY`, пароль БД и
  **настоящие ключи провайдеров** `NOX_UPSTREAM_*_KEY` (они есть только здесь).
- `/etc/nox-portal/provisioner.env` (root, 600) — токен провизионера, адрес шлюза, токен Cloudflare.
- `/etc/nox-portal/provisioner-key.pem` (root, 600) — закрытый ключ. Им провизионер расшифровывает
  ключи шлюза и персональные ключи Anthropic клиентов. Портал хранит их только зашифрованными открытым
  ключом (`/opt/nox-portal/provisioner-pub.pem`) и стирает после успешного задания.

Ключи и токены набирайте прямо на сервере. Не отправляйте их в чаты, тикеты и документы.

## 1. Установка

Нужен облачный сервер с Docker и распакованным релизом iler-bot в `/opt/iler/bundle`
(папка с `compose.yml`, `deploy/` и `images.tar`). Порталу нужна папка `portal/` из того же репозитория.

```sh
cd /opt/iler/bundle            # или клон репозитория iler-bot
sudo bash deploy/cloud/portal-install.sh
```

Скрипт можно запускать повторно: секреты и данные сохраняются, образы пересобираются.
Он создаёт `/opt/nox-portal`, генерирует секреты, поднимает контейнеры (проект `nox-portal`) и ставит
`nox-provisioner.service` с таймером.

Проверка: `curl -fsS http://127.0.0.1:8100/health` выводит `{"status":"ok",...}`.

## 2. Почта (SMTP)

Откройте `sudo nano /opt/nox-portal/.env` и заполните:

```
NOX_EMAIL_MODE=smtp
NOX_SMTP_HOST=smtp.example.kz
NOX_SMTP_PORT=587            # 465 для SSL
NOX_SMTP_SECURITY=starttls   # starttls | ssl | none
NOX_SMTP_USER=bot@example.kz
NOX_SMTP_PASSWORD=...        # пароль ящика или пароль приложения
NOX_SMTP_FROM=Nox service <bot@noxsw.kz>
NOX_SMTP_REPLY_TO=info@noxsw.kz   # необязательно: ответы клиентов уходят в этот ящик
NOX_STAFF_NOTIFY=ops@example.kz,boss@example.kz   # кому писать о новых заявках
```

Затем перезапустите: `sudo bash deploy/cloud/portal-install.sh`.
Чтобы письма не попадали в спам, у домена отправителя должны быть настроены SPF и DKIM.

`NOX_EMAIL_MODE=log` нужен только для проверки на тестовом стенде: письма с кодами и ссылками
пишутся в лог (`cd /opt/nox-portal && sudo docker compose logs api`). На боевом сервере этот режим не включайте.

## 2a. Оплата по счёту и тарифы

На старте клиенты платят по счёту банковским переводом, онлайн-эквайринга нет. Порядок такой:
заявка → код из письма → клиент выбирает тариф → портал выставляет счёт (письмо и страница
`/invoice`, её можно распечатать или сохранить в PDF) → статус «Ждёт оплаты». Когда деньги пришли,
сотрудник нажимает в карточке заявки «Отметить оплату» и вводит сумму и номер платёжки. Платёж
записывается в журнал, а бот сразу встаёт в очередь на создание. Оплата и одобрение — одно действие.

- Тарифы (название, цена в ₸ в месяц, коины) лежат в одном месте:
  `portal/backend/nox_portal/tariffs.py`. Цены в репозитории — заготовки, их нужно утвердить
  до запуска. После правки запустите `portal-install.sh` ещё раз. Уже выставленные счета сохраняют свою сумму.
- Реквизиты продавца для счёта — `NOX_SELLER_*` в `/opt/nox-portal/.env` (название, БИН, банк, ИИК,
  БИК, Кбе, адрес, телефон). В репозитории только заглушки. Срок оплаты — `NOX_INVOICE_DUE_DAYS`.
- Журнал платежей (таблица `payments`) только дополняется: изменить или удалить строку база не даст.
  Ошибку или возврат оформляют новой строкой с отрицательной суммой (пока через SQL, кнопки в интерфейсе нет).
- «Одобрить без оплаты» остаётся для пробного периода и партнёров. Такие одобрения попадают в журнал
  действий с пометкой `payment: null`.

## 3. Cloudflare

### Токен API

Cloudflare → My Profile → API Tokens → Create Token → Custom token:

| Тип | Ресурс | Право |
|---|---|---|
| Account | Cloudflare Tunnel | Edit |
| Zone | DNS | Edit |

В Zone Resources выберите только зону `noxsw.kz`, в Account Resources — только аккаунт Nox.

Также нужны:

- **Account ID** — на странице зоны noxsw.kz справа (Overview → API);
- **Zone ID** — там же;
- **Tunnel ID** — Zero Trust → Networks → Tunnels → `iler-cloud-01` (UUID).

Впишите их в `sudo nano /etc/nox-portal/provisioner.env`: `CF_API_TOKEN`, `CF_ACCOUNT_ID`,
`CF_ZONE_ID`, `CF_TUNNEL_ID`. `NOX_GATEWAY_URL` (по умолчанию `https://bot.noxsw.kz`) — адрес
LLM-шлюза, который получат новые боты (раздел 8). `NOX_DEFAULT_ANTHROPIC_KEY` оставьте пустым: он нужен
только для заданий, поставленных до появления шлюза.

Провизионер для каждого бота:

1. читает конфигурацию туннеля (`GET /accounts/{account}/cfd_tunnel/{tunnel}/configurations`);
2. добавляет правило `<адрес>.noxsw.kz → http://127.0.0.1:<порт>` перед последним правилом
   `http_status:404` и отправляет весь список обратно (`PUT` на тот же адрес). Остальные правила
   сохраняются;
3. создаёт DNS-запись `CNAME <адрес> → <tunnel-id>.cfargotunnel.com` с проксированием (оранжевое облако).

Если на этот адрес уже есть чужая DNS-запись, провизионер её не трогает и выдаёт ошибку.

Проверка настроек (ничего не меняет):

```sh
sudo bash -c 'set -a; . /etc/nox-portal/provisioner.env; python3 /opt/nox-portal/bin/nox-provisioner.py check'
```

После успешной проверки включите таймер: `sudo systemctl enable --now nox-provisioner.timer`.

### Адрес самого портала

Добавьте его один раз вручную: Zero Trust → Networks → Tunnels → `iler-cloud-01` → Public Hostname → Add.
Subdomain `bot`, Domain `noxsw.kz`, Service **HTTP** `127.0.0.1:8100`.

Внутренний порт `8099` в туннель не добавляйте никогда.

## 4. Учётные записи сотрудников

Учётную запись сотрудника можно создать только командой на сервере, на сайте регистрации для них нет:

```sh
cd /opt/nox-portal && sudo docker compose exec api python manage.py create-staff --email ops@example.kz --name "Имя"
cd /opt/nox-portal && sudo docker compose exec api python manage.py set-staff-password --email ops@example.kz
cd /opt/nox-portal && sudo docker compose exec api python manage.py disable-staff --email ops@example.kz
cd /opt/nox-portal && sudo docker compose exec api python manage.py list-staff
```

Пароль вводится скрыто, его длина — не меньше 10 символов. Вход для сотрудников: `https://bot.noxsw.kz/staff/login`.

## 5. Проверка всей цепочки

1. Откройте `https://bot.noxsw.kz/register` и подайте заявку на свою почту с адресом вроде `test-nox`.
2. Введите код из письма и выберите тариф. Придут письмо со счётом и уведомление на `NOX_STAFF_NOTIFY`;
   счёт откроется по кнопке «Открыть счёт (PDF)».
3. Войдите как сотрудник, откройте заявку (фильтр «Ждёт оплаты»), нажмите «Отметить оплату» и
   укажите сумму и номер платёжки.
4. В течение минуты статус станет «Создаётся», а через несколько минут — «Работает».
   Ход работы: `sudo journalctl -u nox-provisioner -f`.
5. Придёт письмо «Ваш бот готов» с адресом панели и одноразовой ссылкой. Откройте
   `https://test-nox.noxsw.kz`: панель должна загрузиться по HTTPS.
6. Удалите тестового бота: в карточке заявки нажмите «Удалить бота» и введите адрес. Проверьте, что
   правило и CNAME исчезли в Cloudflare.

Если создание не удалось, статус станет «Ошибка». Текст ошибки виден в карточке заявки и в
`journalctl -u nox-provisioner`. Исправьте причину и нажмите «Повторить создание». Если бот уже был
установлен, повтор его не пересоздаёт, а только доделывает оставшиеся шаги.

## 6. Резервная копия базы портала

```sh
sudo mkdir -p /opt/nox-portal/backups
cd /opt/nox-portal && sudo docker compose exec -T db pg_dump -U portal -d portal -Fc \
  > /opt/nox-portal/backups/portal-$(date +%Y%m%d-%H%M).dump
```

Ежедневно в 03:00 по Алматы (`/etc/cron.d/nox-portal-backup`):

```
CRON_TZ=Asia/Almaty
0 3 * * * root cd /opt/nox-portal && docker compose exec -T db pg_dump -U portal -d portal -Fc > /opt/nox-portal/backups/portal-$(date +\%Y\%m\%d).dump && find /opt/nox-portal/backups -name 'portal-*.dump' -mtime +14 -delete
```

Вместе с копией базы сохраняйте `/opt/nox-portal/.env` и всю папку `/etc/nox-portal/`. Без
`NOX_SECRET_KEY` не расшифровать неотправленные ссылки владельцев, а без `provisioner-key.pem` —
ключи клиентов, которые стоят в очереди.

Восстановление:

```sh
cd /opt/nox-portal && sudo docker compose exec -T db pg_restore -U portal -d portal --clean --if-exists < portal-YYYYMMDD.dump
```

## 7. Обслуживание

| Задача | Команда |
|---|---|
| логи портала | `cd /opt/nox-portal && sudo docker compose logs -f api web` |
| логи провизионера | `sudo journalctl -u nox-provisioner -n 200` |
| запустить провизионер сейчас | `sudo systemctl start nox-provisioner.service` |
| обновить портал | `git pull` (или новый бандл), затем `sudo bash deploy/cloud/portal-install.sh` |
| остановить портал | `cd /opt/nox-portal && sudo docker compose stop` |

Если провизионер не прислал результат за 30 минут, задание помечается как ошибка с текстом про
таймаут. Тогда посмотрите `journalctl` и нажмите «Повторить».

Порты новых ботов выбираются из диапазона `NOX_PORT_MIN`–`NOX_PORT_MAX` (по умолчанию 8110–8999).
Занятые порты пропускаются: и у работающих, и у остановленных клиентов. Порты 8099 и 8100 занимает
портал.

## 8. LLM-шлюз и коины

Боты не держат настоящих ключей Anthropic, OpenAI и Gemini. Каждый бот получает свой **виртуальный
ключ** `nox_vk_…` и ходит в модели через портал:

| Бот обращается | Портал отправляет |
|---|---|
| `https://bot.noxsw.kz/llm/anthropic/...` | `https://api.anthropic.com/...` |
| `https://bot.noxsw.kz/llm/openai/...` | `https://api.openai.com/...` |
| `https://bot.noxsw.kz/llm/gemini/...` | `https://generativelanguage.googleapis.com/...` |

Шлюз проверяет виртуальный ключ (в `x-api-key`, `Authorization: Bearer` или `x-goog-api-key`; ключ в
адресе `?key=` отклоняется), подставляет ключ компании, пропускает запрос и ответ без изменений (потоковые
ответы — сразу, по событиям) и списывает коины по токенам из ответа. Бот видит баланс через
`GET /llm/v1/balance`. При нулевом балансе шлюз отвечает `402 insufficient_coins` ещё до запроса к
провайдеру, отозванный ключ или приостановленный клиент получают `401 key_revoked`.

Пропускаются только генерация, подсчёт токенов, эмбеддинги и список моделей. Файлы, batch, fine-tuning,
картинки и звук закрыты: их шлюз не умеет считать.

### Настройка (один раз)

В `sudo nano /opt/nox-portal/.env` впишите ключи компании (только здесь, больше нигде):

```
NOX_UPSTREAM_ANTHROPIC_KEY=sk-ant-api03-…
NOX_UPSTREAM_OPENAI_KEY=sk-proj-…
NOX_UPSTREAM_GEMINI_KEY=AIza…
NOX_ALERT_TELEGRAM_BOT_TOKEN=     # необязательно: тревоги и сводка ещё и в Telegram
NOX_ALERT_TELEGRAM_CHAT_ID=
```

Затем `sudo bash deploy/cloud/portal-install.sh`. Провайдер без ключа отвечает ботам `503`.
Ключи Anthropic лучше держать в отдельном workspace `nox-cloud` с автопополнением в консоли.

### Цены и коины

1 коин = $0.001 расхода модели. Таблица цен одна: `portal/backend/nox_portal/prices.py`. В ней те же
цены Claude, что и в ядре бота: claude-sonnet-5-5 — $2/$10 за 1 млн токенов, claude-haiku-5-5 —
$0.1/$0.5. Запись в кэш Anthropic считается как 1,25 цены входа, чтение — 0,1. Цены других моделей задаются в
`NOX_MODEL_PRICES` в том же формате, что `ILER_MODEL_PRICES` у бота:

```
NOX_MODEL_PRICES={"gpt-5.4-mini": [0.25, 2.0], "gemini-3.8-flash": [0.3, 2.5]}
```

Модель без цены никогда не идёт бесплатно: её считают по самой дорогой известной цене того же провайдера.
Если у провайдера нет ни одной цены — по $2/$10, как в ядре. В логе появляется предупреждение, строка
журнала помечается `priced = false`, а в ежедневной сводке перечислены такие модели. **OpenAI и Gemini
встроенных цен не имеют**: впишите их в `NOX_MODEL_PRICES` до запуска клиентов на этих провайдерах.

Каждое списание — строка в `llm_usage`, каждое начисление — в `coin_grants`. Обе таблицы только
дополняются, как `payments`. Баланс клиента складывается так: месячный пакет текущего периода +
остаток докупленных коинов + пополнения − расход.

### Периоды, продление, отсрочка

- Период — месяц с момента активации: оплата первого счёта, одобрение без оплаты или создание локальной
  установки. В начале периода начисляется месячный пакет (лимит коинов заявки, по умолчанию — из тарифа).
- За 5 дней до конца периода (`NOX_RENEWAL_INVOICE_DAYS`) портал выставляет счёт на продление и отправляет
  письмо клиенту и сотрудникам. Сотрудник отмечает оплату в карточке, раздел «Продление и пополнение».
- В конце оплаченного периода начинается новый. Неиспользованный месячный пакет сгорает, докупленные коины
  остаются.
- Если счёт не оплачен, бот ещё 3 дня (`NOX_GRACE_DAYS`) работает на остатке. Потом аккаунт получает статус
  «Приостановлена» (причина «неоплата»): ключ отвечает `401`, облачному боту ставится задание
  приостановки, клиенту и сотрудникам уходят письма. Как только оплату отметят, начинается новый период
  (с этого дня) и ставится задание возобновления.
- Когда остаётся 20% и 5% пакета, клиенту приходит письмо.
- Всё это делает фоновая задача портала (`NOX_BILLING_TICK_SECONDS`, по умолчанию 300 с). Провизионер
  в этом не участвует, он только выполняет задания приостановки и возобновления.

### Пополнение

В кабинете (`https://bot.noxsw.kz/cabinet`, сюда же ведёт кнопка «Пополнить» в админке бота) клиент жмёт
«Пополнить» и получает счёт на пакет 10 000 коинов за 9 900 ₸ (`tariffs.TOPUP`). Пока счёт не оплачен,
повторное нажатие показывает тот же счёт. Сотрудник нажимает «Отметить оплату» у счёта. Коины
начисляются сразу, клиенту уходит письмо.

### Ключи ботов

- **Облако.** При «Отметить оплату» или «Одобрить» портал выпускает ключ и передаёт его провизионеру в
  зашифрованном виде. Провизионер вписывает в `.env` бота (права 600) `ILER_LLM_GATEWAY_URL` (из
  `NOX_GATEWAY_URL`), `ILER_LLM_GATEWAY_KEY` и `ILER_TOPUP_URL` (кнопка «Пополнить» в админке бота, из
  `NOX_TOPUP_URL`), очищает `ILER_ANTHROPIC_KEY` / `ILER_OPENAI_KEY` /
  `ILER_GEMINI_KEY`, ставит `ILER_MONTHLY_COINS=0` (коины считает портал) и перезапускает `iler-core`.
- **Свой ключ Anthropic клиента** (поле при одобрении) по-прежнему работает и имеет приоритет. Тогда шлюз
  не используется: виртуальный ключ не выпускается, переменные шлюза не пишутся, коины портал не считает.
- **«Перевыпустить ключ»** (карточка, раздел «LLM-шлюз»). Облачный бот получает задание «Новый ключ
  шлюза»: новый ключ вписывается в `.env` и ядро перезапускается. Старый ключ отключается только после
  успеха, если задание упало — отключается новый. Так же можно перевести на шлюз старого бота с ключом
  Anthropic в `.env`: после задания ключ компании на нём не останется. Для облачного бота кнопка
  доступна, только когда бот работает.
- **«Отозвать»** отключает все ключи сразу: бот получает `401` на каждый запрос к модели.
- В карточке видно только начало ключа (`nox_vk_AbCdEf…`). Целиком ключ портал не хранит: в базе лежит
  только его хэш SHA-256.

### Локальная установка (бот у клиента)

1. Сотрудник: «Заявки» → «Локальная установка». Заполните компанию, контакт, e-mail, короткое имя и
   тариф. Портал создаёт активный аккаунт без заданий провизионера и **один раз** показывает ключ.
   Клиенту уходит письмо о том, как задать пароль кабинета (через «Забыли пароль»).
2. Передайте ключ технику, не через мессенджеры. Если ключ потерян, нажмите «Перевыпустить ключ»: у
   локальной установки старый отключится сразу.
3. Техник на компьютере клиента вписывает в `/opt/iler/.env` две переменные ядра бота и перезапускает его:

   ```
   ILER_LLM_GATEWAY_URL=https://bot.noxsw.kz
   ILER_LLM_GATEWAY_KEY=nox_vk_…
   ```

### Тревоги и сводка

Сотрудникам из `NOX_STAFF_NOTIFY` и в Telegram (если задан) уходят тревоги:

- провайдер отклонил ключ компании (`401`/`403`): проверьте `NOX_UPSTREAM_*_KEY`;
- закончились деньги или квота у провайдера (`402`, «credit balance», «insufficient_quota»): пополните
  консоль;
- 5 и больше ошибок 5xx или таймаутов за 5 минут (`NOX_ALERT_ERROR_THRESHOLD`, `NOX_ALERT_WINDOW_SECONDS`).

Одна и та же тревога повторяется не чаще раза в 30 минут. Каждый день после 09:00 по Алматы приходит
сводка за вчера: коины и доллары по провайдерам, токены, модели без цены. Сверяйте её с консолями
провайдеров. Токен Telegram в логи не попадает.

### Ограничения

- 60 запросов в минуту на ключ (`NOX_GATEWAY_RATE_PER_MINUTE`), запрос до 10 МБ (`NOX_GATEWAY_MAX_BODY_BYTES`;
  в `portal/web/nginx.conf` стоит тот же `client_max_body_size 10m`). При превышении шлюз отвечает `429` или `413`.
- Параллельные запросы одного клиента могут уйти в минус не больше чем на один запрос. Перед запросом
  резервируется верхняя оценка его цены, а при нулевом остатке после всех резервов шлюз отвечает `402`.
  Небольшой минус прощается при смене периода.
- Если клиент не попросил usage в потоке OpenAI Chat Completions, шлюз добавляет
  `stream_options.include_usage` и не пересылает клиенту лишний последний чанк с пустым `choices`.
- У OpenAI кэшированные входные токены считаются по полной цене входа. Токены «размышлений» Gemini
  (`thoughtsTokenCount`) считаются как выход.

### Проверка на своём компьютере (mock, без настоящих ключей)

`portal/smoke/` содержит фальшивый API провайдеров и сценарий проверки. Скопируйте `portal/.env.example` в
`portal/.env`, задайте `NOX_SECRET_KEY` (`openssl rand -base64 32`), `NOX_DB_PASSWORD`,
`NOX_EMAIL_MODE=log`, `NOX_PUBLIC_URL=http://127.0.0.1:18100`, `NOX_HTTP_PORT=18100`,
`NOX_INTERNAL_PORT=18099`. Положите любой открытый RSA-ключ в `portal/provisioner-pub.pem` и выполните:

```sh
cd portal
docker compose -p nox-smoke -f compose.yml -f smoke/compose.smoke.yml --env-file .env up -d --build
bash smoke/run.sh
docker compose -p nox-smoke -f compose.yml -f smoke/compose.smoke.yml --env-file .env down -v
```

Сценарий выпускает ключ локальной установки с балансом 5 коинов и делает через nginx запросы: Anthropic
обычный и потоковый, OpenAI потоковый, Gemini. Затем проверяет `?key=`, журнал списаний и баланс, а в
конце — `402` после исчерпания баланса. `.env` и `provisioner-pub.pem` после проверки удалите.
